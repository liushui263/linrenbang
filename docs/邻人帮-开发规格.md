## 0. v3 相对 v2 改了什么

1. **改名：Houston邻居帮 → 邻人帮。** 名字里不带城市名，才能扩展到其他城市。备选是邻里帮、帮邻，但首选邻人帮：三个字、好念、好记，“邻人”比“邻里”更像人，“帮”就是动作。英文名 Linren Bang，不要翻译成 Neighbor Help（太普通、难注册）。
2. **第一次打开先问 Zip Code。** 用户首次打开输入 5 位 Zip，或点“更改 Zip”，自动切换到当地信息。MVP 只开通休斯顿，其他 Zip 进来显示“你所在城市还没开通，留个邮箱，有消息通知你”，同时允许继续浏览休斯顿（标明“当前查看：休斯顿”）。数据库和配置从第一天就按多城市设计，不要写死休斯顿。
3. **分类从 9 个扩到 12 个。** 新增三个休斯顿华人高频需求：房产经纪、贷款/Title/过户、餐饮美食。注意：餐饮只是推荐餐馆（哪家好吃、谁推荐的、电话/微信），**不做在线订餐、不接外卖系统**；房产只是推荐经纪人，**不接 MLS 房源**；贷款/Title 只是推荐贷款员和 Title 公司，**不报实时利率**。这三个分类和修空调一样：只做名片 + 推荐 + 电话。
4. **广告收费整段删掉，换成“前 100 + 每类前 10 轮换”。** v2 的 $39/$79、Zelle/Venmo 收款、`/merchant/ads` 全部不要。规则见第 6 节：前 100 名审核通过的商家是“创始商家”，每分类最先通过的 10 家进入轮换池，每天轮换着上首页和分类页顶部。公平、不花钱、先到先得，冷启动的钩子就是这个。**创始身份有效期 100 天，自审核通过日起算，到期自动失效**——不是永久的，过期后名片上的创始角标消失、退出轮换池，恢复按推荐数正常排序。这样 100 天后轮换位和置顶位都空出来了，以后想做付费置顶也不会被永久免费位占住。
5. **每个商家是一张名片。** 列表里的卡片和详情页都按名片设计，一眼能看清：是谁、干什么、在哪片、多少邻居推荐、怎么联系。见第 8 节的名片版式，Claude 按那个版式做，不许自己发挥成黄页列表。
6. **收款方式改了：微信收不了钱。** 站长微信不收款。以后收费时再定 PayPal / Zelle / Cash App / Venmo，v3 代码里不留支付字段、不留收款页。站长另申请一个专门负责邻人帮的微信号，只用来联系商家和用户，不和私人微信混用。表单里已改。
7. **星级和商家数据看板继续不做。** 原因写在第 1 节，Claude 不要偷偷加上。

## 1. 为什么不做星级、不做商家数据看板

这不是“能不能做”，是“做了会把产品带偏，而且拖慢上线”：

**星级评分：**
- 一个 5 星、一个 1 星，平均分毫无意义。新商家只有 1 条评价就是 5 星，老商家 20 条里有一条 1 星就掉到 4.6，用户根本看不懂，排序也会被带偏。要做得可信，得做贝叶斯平均、验证消费、剔除恶意差评，一套下来比推荐系统本身还复杂。
- 星级没有信息量。用户真正想看的是“修了什么、花了多少钱、等了多久”，一句话推荐比 5 颗星有用。星级还会让人以为平台在背书——“平台给了 4.9 星，出问题你负责？”推荐数 + 原文不背书，只呈现邻居原话，责任边界干净。
- 星级最容易刷：注册几个号打 5 星，比写 20 条像真人写的推荐容易得多。

**商家数据看板：**
- 看板不是一个页面，是一条链：浏览量、电话点击、微信复制、搜索曝光都要埋点、存表、聚合、画图、做权限、做导出。MVP 商家真正需要的只有三件事：我的信息对不对、多少人推荐了我、我的置顶/轮换什么时候到。这三件事在 `/merchant` 一个极简页上就能看，不需要图表。
- 看板还会逼你回答商家的问题：“为什么昨天只有 3 个浏览？”你答不上来，反而伤信任。先让商家拿到电话和推荐，数据以后再说。

所以 v3 只保留：推荐数（数字）+ 推荐原文（文字）。商家端只保留：编辑名片 + 看推荐数 + 看轮换状态。

## 2. 产品定位与多城市设计

- **一句话：** 找本地靠谱的华人服务，先看邻居推荐，再打电话。
- **首站：** 休斯顿。以后扩展到达拉斯、奥斯汀、纽约、洛杉矶等，不用改名、不用重构。
- **城市切换（Zip Code）：**
- 首次打开：全屏轻提示“输入你的 Zip Code，看看你附近的邻居推荐了谁”，输入 5 位数字即可，不强制登录，不许用定位权限逼用户。
- 存两处：`localStorage`（游客）+ `users.home_zip`（登录用户）。
- Zip → 城市映射写在 `constants/cities.ts`：休斯顿覆盖 `770xx / 773xx / 774xx / 775xx` 开头（以后按实际再细化）；不在映射里的 Zip → 城市状态为 `coming_soon`，显示“你所在城市还没开通，留个邮箱通知你”，同时顶部显示“当前查看：休斯顿”，用户可手动切回休斯顿浏览。
- 顶部常驻：当前城市名 + Zip + 按钮，点开可改 Zip。
- 商家注册时也要填服务城市（默认当前城市），`providers.city_id` 必填。搜索、筛选、轮换全部先按 `city_id` 过滤，再按片区/分类。
- **非目标（v3 不做）：** 在线支付、在线订餐、MLS 房源、实时利率、下单派单、在线聊天、星级、商家数据看板、App。

## 3. 技术栈（锁死）

- Next.js 14+ (App Router) + TypeScript + Tailwind CSS，部署 **Vercel**（先用 Vercel 免费域名上线，以后再绑自己的域名，换托管也不用改代码）
- Supabase：PostgreSQL + Auth（**只开 Google 登录**；手机号短信 OTP 和微信登录 v3 暂不开通，登录页按钮灰显“暂不支持”，见 13.5）+ Storage（商家头像、执照照片）
- 不用 Prisma，不用 tRPC
- 环境变量：`NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_ROLE_KEY`（只在服务端用）

## 4. 数据库（4 张核心表 + 1 个城市配置，Supabase SQL）

城市不单独建表（MVP 城市少），用常量 + 字段控制；商家量上来后再把城市抽成表。

**`users`**：`id` / `email` / `phone`（E.164）/ `phone_verified` / `display_name` / `neighborhood` / `home_zip`（varchar(10)）/ `home_city_id`（varchar(20)，默认 `'houston'`）/ `role` / `created_at` / `updated_at`

**`providers`**（在 v2 基础上加 4 个字段）：
- `city_id` varchar(20) not null 默认 `'houston'`，索引
- `home_zip` 不需要，服务范围用 `service_areas` + `service_zips` text[]（选填，如 `["77077","77494"]`）
- `avatar_url` text nullable（商家头像，Supabase Storage）
- `tagline` varchar(60) nullable（一句话名片标语，如“15 年中央空调，Katy 很多家都是我装的”）
- `is_founding` boolean 默认 false（前 100 名审核通过的商家，且在 100 天有效期内）
- `founding_rank` int nullable（第几名通过，1-100，历史名次永久保留，只作记录）
- `founding_started_at` timestamptz nullable（审核通过时间）
- `founding_expires_at` timestamptz nullable（= `founding_started_at` + 100 天；查询时只认 `now() < founding_expires_at` 的才算有效创始）
- `category_rank` int nullable（本分类第几名通过；轮换资格按“本分类、创始有效期内、通过时间最早的 10 家”每天动态算，不要只认静态的 1-10）
- 其余字段同 v2：`owner_user_id` / `submitted_by_user_id` / `source` / `name` / `category` / `sub_tags` / `service_areas` / `phone`（unique，E.164）/ `wechat_id` / `languages` / `is_licensed`（自称）/ `license_number` / `license_photo_url` / `license_status`（`unclaimed` / `self_claimed` / `doc_uploaded` / `verified`，仅站长人工改，MVP 几乎不用）/ `is_insured` / `emergency_24h` / `price_note` / `description` / `recommend_count`（trigger 维护，只计 active）/ `is_claimed` / `status`（`pending` / `active` / `hidden`）/ `created_at` / `updated_at`

**`recommendations`**：同 v2。`provider_id` / `user_id` / `recommender_area` / `service_item` / `cost_approx` / `comment`（300 字内）/ `status`（`pending` / `active` / `hidden`）/ 联合唯一 `(provider_id, user_id)`。

**`ad_placements`**：v3 不收费，但表保留，改用途：只存轮换记录，不存钱。
- `slot_type`：`home_rotation` / `category_rotation`（不再有 `home_banner` / `category_top` 付费位）
- `is_free_grant` 恒为 true，`amount_cents` 恒为 0，`paid_via` / `paid_at` 留空（不要删字段，以后收费时再用）
- `start_at` / `end_at`：轮换档期，如当天 00:00–23:59
- 其余同 v2。轮换记录由系统每天自动生成（见第 6 节），站长不用手工录。

### 索引与约束（同 v2，再加）
- `providers(city_id, category, recommend_count)` 复合索引；`providers.phone` UNIQUE；`service_areas` / `sub_tags` GIN；`name` / `description` trigram 索引（`pg_trgm`，中文搜索用这个）
- `CHECK (end_at > start_at)`；推荐数 trigger 同 v2

### RLS（同 v2）
匿名可读 active / paused 商家的公开字段（**不含 `phone`、`wechat_id`，见 13.6**）/active 推荐/未过期轮换；登录用户可写自己的推荐、可改自己名下的商家；新商家强制 `pending`；`ADMIN_USER_IDS` 白名单才能改状态、改 `license_status`、改轮换。

## 6. 创始商家与轮换推荐（代替广告收费）

- **创始商家：** 按审核通过时间排序，前 100 名 `is_founding=true`，`founding_rank=1..100`，`founding_started_at`=通过时间，`founding_expires_at`=通过时间 + 100 天。名片上显示金色角标 `创始商家 #N · 还剩 X 天`。第 101 名起不再发，页面文案自动变成“创始名额已满”。**创始身份有效期 100 天，到期自动失效**：过期后角标消失，`is_founding` 在查询时按 `now() < founding_expires_at` 判断为 false（`founding_rank` 只作历史记录保留）。商家本身不下架，过期后按推荐数正常排序。
- **轮换池（滚动的，不是占死的）：** 每天按“本分类、创始有效期内、通过时间最早的 10 家”动态取轮换池。前面的人 100 天到期退出后，后面第 11、12 名自动递补进来，不用站长手工操作。第 11 名起在有效期内没进池时，正常展示、按推荐数排序。
- **轮换规则（写死，不要搞复杂算法）：**
- 每天 00:00（按美国中部时间）轮换一次。当天轮换名单 = 轮换池按 `(天数 + category_rank) % 10` 取 2 家，首页和分类页共用同一份名单。
- 首页顶部“今日邻人推荐”放 2 条轮换（不同分类各 1 条优先）；分类页顶部放该分类当天的 2 条轮换。
- 轮换卡片角标写 `今日推荐`，不要写“置顶推广”（没人付钱，就不要像广告）。
- 轮换记录每天自动写一条 `ad_placements`（`slot_type=home_rotation/category_rotation`，当天起止），供站长查，不用人工操作。
- **排序（轮换之后）：** 轮换 2 条 → 其余按 `recommend_count` 降序 → `created_at` 降序。每页 20 条。

## 7. 业务流程

### 7.1 商家自助注册（主流程）
`/merchant/register`：先 Google 登录 → 填表 → 提交 pending → 站长 `/admin` 一键通过 → 自动算创始名次和分类名次（前 100 / 前 10 自动进池）→ 首页可见。
填表字段：店名/称呼*、主营分类*（12 选 1）、服务城市*（默认当前城市）、覆盖片区*（多选）、电话*（E.164，全站唯一；v3 不发短信验证，站长审核时核对；提交后要改号需联系站长）、微信号（选填）、头像（选填，上传）、一句话标语（选填，60 字内）、细分技能标签（最多 6 个）、语言、是否自称有执照（可填执照号、可传照片）、是否有保险、是否 24 小时急修、收费说明（150 字内）、简介（300 字内）。
提交成功页写清：“已提交，站长一般 24 小时内审核。审核通过后按通过顺序算创始名次，前 100 名是创始商家，有效期 100 天（自通过日起算，到期后恢复正常排序），每分类前 10 名进每日轮换。”

### 7.2 邻居代录入 / 认领（辅流程，同 v2）
电话查重 → 已存在跳详情页写推荐；不存在 → 登录 → 填商家 + 推荐 → 商家 pending、`source='neighbor_submitted'`。商家本人 Google 登录后在 `/merchant/claim` 提交认领申请，站长通过电话或微信核实本人后在 `/admin` 一键通过（v3 不用短信 OTP 认领）。

### 7.3 邻居写推荐（信任核心，同 v2）
Google 登录 → 片区*、修了什么、花了多少钱、推荐理由*（300 字内）→ pending → 站长通过后展示、计入推荐数。一人一商家只能推荐一次，可编辑自己那条。商家不能给自己写推荐。

### 7.4 举报 / 纠错 / 下架（同 v2）
每商家、每推荐都有举报按钮；商家本人登录后申请下架（或通过站长微信申请），站长核实后处理；站长 24 小时内处理，先隐藏再核实。页脚固定免责声明（见 v2 第 5.4 节）。

## 8. 商家名片（版式，Claude 按这个做）

每个商家在列表和详情页都是一张名片，不是黄页行。`components/ProviderCard.tsx` 一个组件两处复用，详情页是名片的展开版。

**名片版式（从上到下）：**
1. 第一行：头像（圆形，无头像显示姓名首字）+ 名字（加粗大字）+ 分类小徽章（如“空调暖气”）
2. 第二行：`🔥 N位邻居推荐` + 创始角标（`创始商家 #N · 还剩 X 天`，仅 100 天有效期内）/ `今日推荐`（仅当天轮换）+ 执照文案（仅自称有时显示灰色“自称有执照 · 未经核实”，没有就不显示）
3. 第三行：一句话标语（`tagline`，没有则显示简介前 60 字）
4. 第四行：技能标签（最多 3 个，`换热水器 · 通下水道 · 漏水抢修`）
5. 第五行：小字 `服务：Katy, Sugar Land` + `语言：国语` + 急修红标（仅 `emergency_24h`）
6. 第六行：收费提示（`price_note`，小字灰色）

## 13. v3.1 补充技术规范（必须严格执行）

### 13.1 每日轮换算法（实时计算，免 Cron Jobs）
- **不要配置 Vercel Cron Jobs**，也不要依赖后台定时脚本触发轮换。
- 轮换名单采用**无状态实时日期算法**计算，确保同一美国中部时间（`America/Chicago`）自然日内所有用户看到的轮换结果完全一致，过零点自动切换：
  1. 获取当前美国中部时间（`America/Chicago`）的 `YYYY-MM-DD` 日期字符串，计算自 `2026-01-01` 起经过的整数天数 `dayIndex`。
  2. 查询当前城市（`city_id`）及目标分类（`category`）下，满足 `status = 'active'` 且 `now() < founding_expires_at` 的有效创始商家，按 `founding_started_at ASC` 取前 10 家构成轮换池 `pool`（按顺序赋予局部索引 `0 .. pool.length - 1`）。
  3. 若 `pool.length === 0`，则不展示“今日推荐”轮换区；若 `pool.length <= 2`，则全部展示；若 `pool.length > 2`，则取索引为 `dayIndex % pool.length` 和 `(dayIndex + 1) % pool.length` 的 2 家作为当天轮换商家。
  4. **首页轮换**：从当前城市各分类当天的轮换结果中聚合，优先挑选不同分类的 2 家展示在“今日邻人推荐”区域。
  5. **历史记录留存（Lazy Write）**：当某天首次请求触发轮换计算时，后台异步检查 `ad_placements` 表是否已有当天 `America/Chicago` 日期的记录；若无则顺带插入当天的轮换记录（`is_free_grant = true`, `amount_cents = 0`），供站长在后台查看，无需人工干预。

### 13.2 微信内转发与动态 Open Graph（OG Metadata）
- 考虑到用户主要通过微信群和朋友圈转发链接，必须使用 Next.js App Router 的 `generateMetadata` API 为核心页面配置完整的 Open Graph 标签（`og:title`、`og:description`、`og:type`、`og:url`、`og:image`）：
  1. **首页 `/`**：
     - `title`: `邻人帮 · 本地靠谱华人服务推荐`
     - `description`: `空调、水电、屋顶、庭院、搬家、房产经纪、贷款过户、餐馆——先看邻居真实推荐，再打电话。`
  2. **商家详情页 `/provider/[id]`（动态生成）**：
     - `title`: `邻居推荐：${provider.name}（${categoryName}）- 邻人帮`
     - `description`: `${provider.recommend_count}位邻居推荐 · 服务区域：${provider.service_areas.join(' / ')}。${provider.tagline || provider.description?.slice(0, 50) || ''}`
  3. **静态默认分享图**：在 `public/og-default.png` 放置一张 1200x630 的简洁品牌分享卡片（可使用 SVG 转 PNG 或 Next.js `ImageResponse` 动态生成），确保微信转发链接时始终显示图文卡片而非空白链接。

### 13.5 登录方式（v3.2，只开 Google）
- **v3 只开 Google 登录**（Supabase Auth → Google provider）。邻居写推荐、商家注册、商家认领、站长后台全部用 Google 登录。
- 登录页同时显示三个按钮，后两个灰显禁用，旁边小字“暂不支持”：
  1. 【Google 登录】（可用）
  2. 【手机号验证码登录】（灰显 · 暂不支持）
  3. 【微信登录】（灰显 · 暂不支持）
- **为什么暂缓短信 OTP：** 美国给手机发验证码要走 A2P 10DLC 注册（Twilio 需登记品牌和用途，审核要几天到几周，还有月费），冷启动阶段不值得。以后要开时，只需在 Supabase Auth 里打开 Phone provider、把按钮改成可用，表结构不用改（`users.phone` / `phone_verified` 字段先保留）。
- **信任规则相应调整：** 推荐人必须 Google 登录；一个 Google 账号对一个商家只能推荐一次；一个 Google 账号只能拥有一个商家；商家电话靠 `providers.phone` UNIQUE 防重复，由站长审核时核对。
- 不要做邮箱密码登录、不要做魔法链接登录，不要 Mock 登录。

### 13.6 电话与微信防爬（v3.2）
- **不要把商家的 `phone`、`wechat_id` 写进任何页面的 HTML、RSC payload、`__NEXT_DATA__`、JSON-LD 或 OG 标签里。** 列表页和详情页服务端渲染时只取公开字段。
- **数据库层：** 匿名角色不能直接 `select` `providers.phone` / `providers.wechat_id`。做法二选一：建一个不含这两列的视图 `providers_public` 给前端查；或者对 anon / authenticated 角色做列级 `REVOKE SELECT (phone, wechat_id)`。商家本人（`owner_user_id`）和 `ADMIN_USER_IDS` 仍可看全部字段。
- **取联系方式接口：** `GET /api/providers/[id]/contact`（服务端 Route Handler，用 service role 查），只对 `status = 'active'` 的商家返回 `{ phone, wechat_id }`；`pending` / `hidden` 返回 404，`paused` 返回 `{ paused: true }`。响应头 `Cache-Control: no-store`。
- **轻量限流：** 同一 IP 每小时最多取 30 次联系方式，超了返回 429，前端提示“操作太频繁，请稍后再试”。MVP 可以用 Supabase 一张 `contact_reveals(ip_hash, provider_id, created_at)` 表计数（IP 存哈希，不存明文），不用引入 Redis。
- **前端交互：**
  - 【一键拨号】：点击后请求接口，拿到号码立即跳转 `tel:` 链接，同时按钮上显示号码，方便用户手抄。
  - 【复制微信】：点击后请求接口，拿到微信号后复制到剪贴板并 Toast“已复制微信号：xxx”；如果浏览器拒绝异步复制（微信内置浏览器、iOS Safari 常见），改为弹出小框显示微信号 + 【复制】按钮，用户再点一次即可。
  - 匿名用户可以点，不强制登录（降低门槛，防爬靠接口和限流）。
- **其他泄露点一起堵：** 7.2 代录入的“电话查重”接口只返回“已存在 + 商家 id”或“不存在”，不返回该商家其他字段；搜索不支持按电话号码搜索；`sitemap.xml` 只含商家页 URL，不含联系方式。

### 13.7 “其他服务”分类（v3.3）
- 在 12 个固定分类之后加第 13 个：`other` 其他服务，首页分类网格里排最后。给暂时没有专门分类的服务用，比如网站设计、钢琴课、报税。
- **商家必须填服务名**：`providers.custom_service varchar(12)`，选“其他服务”时必填，2-12 个字，不能有网址；数据库加约束 `category <> 'other' or length(trim(custom_service)) >= 2`。选别的分类时这个字段存空。
- **显示规则**：名片的分类徽章、详情页、微信分享卡片标题（`邻居推荐：{商家名}（{服务名}）`）、推荐页都显示商家填的服务名，不显示“其他”。首页筛选“其他服务”时，列出所有 `category = 'other'` 的商家。
- **搜索**：搜索也匹配服务名。
- **轮换**：“其他服务”和固定分类一样，有自己的前 10 名轮换池。
- **站长后台**：待审核列表里，“其他服务”的商家加紫色标签；后台顶部统计“其他服务”里各个服务名出现了几家，出现多的以后可以升级成正式分类（升级时把这些商家的 `category` 改成新分类即可）。
- **数据库迁移**：`supabase/migrations/0002_other_category.sql`，部署新代码前先在 Supabase 运行。

### 13.8 联系方式偏好与发短信（v3.4）
- **为什么**：很多师傅干活时接不了电话，更愿意先收短信或微信；顾客也常常想先发个短信问价。
- **三种方式**：打电话（`tel:`）、发短信（`sms:`，用同一个电话号码）、加微信（复制微信号）。
- **商家自己选**（注册页、`/merchant` 编辑页）：
  - “顾客怎么联系你”：打电话 / 发短信 / 加微信，**可多选，至少选一种**；选了加微信必须填微信号。
  - “最希望顾客用哪种”：单选，必须是上面勾选了的一种。
  - 邻居代录入时不问，默认“打电话 + 发短信”（填了微信号再加“加微信”），偏好打电话；商家认领后可以自己改。
- **数据库**：`providers.contact_methods text[]`（默认 `{phone,sms}`）、`providers.contact_pref varchar(10)`（默认 `phone`），约束：至少一种、只能是这三个值、偏好必须在已选里、选了微信必须有微信号。两列对前端开放读取（不含号码本身）。迁移：`supabase/migrations/0003_contact_pref.sql`，部署新代码前先运行；老商家自动设为“电话 + 短信”，有微信号的再加“微信”，偏好电话。
- **名片显示**：只显示商家勾选的方式；偏好的按钮排第一、实心绿色；不止一种时按钮上方标 `★ 偏好短信联系` / `偏好电话联系` / `偏好微信联系`。点过以后按钮下方小字显示号码和微信号，方便手抄。
- **发短信**：链接用 `sms:+1XXXXXXXXXX?&body=你好，我在邻人帮看到你的名片，想咨询一下：`（这种写法 iPhone 和安卓都认），商家一看就知道是从邻人帮来的。
- **防爬不变**：短信号码和电话一样，点按钮才从 `/api/providers/[id]/contact` 取；接口只返回商家勾选了的方式（没勾电话也没勾短信就不返回号码，没勾微信就不返回微信号）。`paused` 时所有联系按钮一起变灰。
- **站长后台**：待审核列表显示“联系：打电话 / 发短信 · 偏好短信联系”。
